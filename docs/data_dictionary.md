# Cafe Fausse -- Data Dictionary

## Scope and authority

This data dictionary describes the PostgreSQL tables required by SRS FR-17. It is derived from [schema.sql](schema.sql) and [database_design.md](database_design.md). It documents the approved schema; it does not introduce additional fields.

## Entity: `customers`

Stores one customer identity and that customer's newsletter preference.

| Attribute | PostgreSQL type | Null? | Key / constraint | Business meaning | Example |
|---|---|---:|---|---|---|
| `customer_id` | `SERIAL` | No | Primary key; generated by PostgreSQL | Unique identifier for a customer | `42` |
| `customer_name` | `VARCHAR(100)` | No | Required | Name supplied with a reservation; newsletter-only signups use `Newsletter Subscriber` | `Avery Chen` |
| `customer_email` | `VARCHAR(255)` | No | Required; unique | Customer contact email and the database-level customer de-duplication key. The API trims and lowercases it before lookup/storage. | `avery@example.com` |
| `phone_number` | `VARCHAR(20)` | Yes | Optional | Customer phone number for a reservation | `(202) 555-0100` |
| `newsletter_signup` | `BOOLEAN` | No | Defaults to `FALSE` | Whether the customer has opted into the newsletter | `TRUE` |

## Entity: `reservations`

Stores one table booking for one customer at one time slot.

| Attribute | PostgreSQL type | Null? | Key / constraint | Business meaning | Example |
|---|---|---:|---|---|---|
| `reservation_id` | `SERIAL` | No | Primary key; generated by PostgreSQL | Unique identifier for a reservation | `108` |
| `customer_id` | `INTEGER` | No | Foreign key to `customers.customer_id`; `ON DELETE CASCADE` | Identifies the customer who made the booking | `42` |
| `time_slot` | `TIMESTAMP` | No | Required | Requested restaurant-local date and time; the approved schema is timezone-naive | `2026-12-01 19:00:00` |
| `table_number` | `INTEGER` | No | Must be between 1 and 30 | Randomly assigned table number from the fixed pool of 30 tables | `17` |

## Table-level constraints and business rules

| Rule | Enforced by | Why it matters |
|---|---|---|
| A customer email occurs once only. | `UNIQUE (customer_email)` | Prevents duplicate customer records for the same normalized email. |
| A table is booked at most once per time slot. | `UNIQUE (time_slot, table_number)` | Prevents double booking under concurrent requests. |
| A reservation references an existing customer. | Foreign key | Preserves the one-customer-to-many-reservations relationship. |
| A table number is 1 through 30. | `CHECK (table_number BETWEEN 1 AND 30)` | Keeps assignments inside the SRS-required table pool. |
| Guest count is 1 through 30, but is not stored. | React and Flask validation | FR-6 requires the input; FR-17 does not include a guest-count database column. |

## De-duplication boundary

PostgreSQL enforces the two unique constraints above; it does not infer which records a business considers duplicates. A repeated newsletter signup is treated as an idempotent update by the Flask API. A repeated reservation request can create a separate valid reservation at another available table because this project intentionally has no reservation idempotency key.
